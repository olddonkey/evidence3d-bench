# v1 首轮测试集结果（2026-10-03 至 10-04）

这是 v1 第一份可以当作测试成绩的结果：题目来自评分器冻结之后才生成的私有测试集，评分器、生成器和运行器在整个过程中没有改动。

## 条件

- **题集** `test-2026-10`：24 个对象，8 类各 3 个，种子取自系统随机源，对象 id 不透明，种子文件不在版本库里。在冻结提交 `74eae6b` 之后生成。
- **题型**：每个对象 `t2`（四张照片加航拍）、`t4`（再加带比例尺的图纸和勘测笔记）、`c1`（照片加过期图纸），共 72 道题。
- **配置**：
  - Codex CLI 0.159.2：`gpt-6-astra`（high），每题 3 次；`gpt-5.6-luna`（high），每题 1 次。
  - Claude Code 2.1.285：`claude-opus-5-5`（high），每题 3 次；`claude-haiku-4-5-20251001`（默认），每题 1 次。
- 共 576 次计分作答，每次 30 分钟墙钟上限，全新会话，隔离预检四个批次全部通过，没有一次触发完整性问题。
- 评分器 1.1.0（源码哈希 `1e37d11cadd3`），所有报告都带这个标记。
- 批次：`.local/v1/runs/test1-{astra,opus,luna,haiku}`；报告：`.local/v1/reports/test1/`（`index.html`、`summary.md`、`leaderboard.json`）。

## 噪声在哪里

| 配置 | 同题多次作答之间的标准差 | 对象之间的标准差 |
|---|---|---|
| astra | 4.6（144 自由度，95% 范围 4.1–5.2） | 3.7 |
| opus | 4.7（144 自由度，95% 范围 4.3–5.4） | 5.7 |
| luna | 无法估计（每题一次） | 8.2 |
| haiku | 无法估计（每题一次） | 9.4 |

- 同一模型对同一道题重做一次，分数的标准差约 4.7 分。这是单次作答的不确定度：只跑一次的话，两个模型在一道题上差 10 分以内都不足以说明什么。
- Astra 对 Opus 的每对象分差标准差是 5.1。按这个设计（24 个对象、每题 3 次），观测分差超过 2.1 分区间就不含零；真实差距 3.0 分时有约 80% 的把握检出。作答噪声只占这个方差的约 19%，其余是"哪个模型更擅长哪个对象"的差异。所以要提高分辨率，加对象比加重复次数更有效。

## 失败与重跑

**无效交付**：只有 Haiku 有，4 次，都是 GLB 文件本身不合规（缓冲区长度或索引越界），记 0 分。四个配置在最终样本里都没有超时。

**基础设施错误**不算样本，归档后从干净的工作目录重跑：

| 批次 | 运行器自动识别并重跑 | 按主机睡眠规则改标并重跑 |
|---|---|---|
| astra | 网络 2 | 8 |
| opus | 网络 3，用量限额 3 | 0 |
| luna | 网络 1，CLI 无响应 1 | 1 |
| haiku | 网络 1 | 1 |

**用量限额**：Opus 批次完成约 200 次时触到 Claude 订阅的周限额。运行器正确识别，把 3 次受影响的作答归档，进入等待；额度恢复后续跑完成。这是限额处理第一次遇到真实情况。

**主机睡眠**：运行期间电脑两次合盖睡眠（10 月 3 日 13:11–13:58 和 21:05–21:42，英国时间；系统电源日志记录了 7 段睡眠）。睡眠时计时器不走，醒来的一瞬间过期的作答被一起判为超时。日志里的唤醒时刻和这些"超时"时刻逐秒吻合。Claude Code 在唤醒后报了网络重试，被运行器识别为网络错误并重跑；Codex 没有，于是 Astra 有 5 次被记成了 0 分的超时。

为此定了一条只看时间、不看分数的规则：**作答期间主机睡眠达 30 秒以上，或实际用时超过上限 60 秒以上的，不算在规定条件下完成，改标为基础设施错误并重跑。** 共 10 次作答受影响：5 次是 Astra 被记成 0 分的超时，另 5 次原本有分（Astra 的 86.4、80.6、77.1，Luna 的 43.0，Haiku 的 29.1），一样重跑。原始记录保留在各作答目录的 `result.host-suspended.json` 和归档目录里。规则是在 Astra 只完成 116 次时定下的，依据只有时间戳和电源日志；当时我已经看过一份中间报告，这一点如实记下。工具是 `v1/scripts/host-sleeps.py` 和 `v1/scripts/relabel-host-suspended.mjs`；运行器本身没有改动。

**机器负载**：运行期间这台机器上有其他项目的测试在跑，负载时高时低。1 分钟负载均值在 30 以上的作答，Astra 有 12 次（均分 70.7，其余 73.6），Opus 有 26 次（均分 62.6，其余 67.1）。只看低负载下的作答，两者的差距是 6.5 分，与总体的 6.9 分接近，所以负载解释不了 Astra 和 Opus 之间的差距。高负载下分数略低是真的受了影响，还是恰好轮到了较难的对象，这份数据分不清。

## 这份数据说明了什么

- 这个 benchmark 能把四个配置两两分开，包括试点时分不开的 Astra 和 Opus：差 6.9 分，Astra 在 24 个对象中的 23 个上更高。
- 排名与开发集上的排名一致，分数也接近（开发集重新评分后是 74.9 / 68.8 / 40.4 / 26.4，测试集是 73.4 / 66.5 / 40.1 / 24.0）。评分器在开发集上调过容差，但没有因此在测试集上走样。
- 单次作答的噪声约 4.7 分。每题只跑一次的结论不可靠，但对"分清两个模型"来说，对象数量比重复次数更要紧。
- 冲突题给出了一个与主分不同的信号：面对互相矛盾的资料时，模型是否以题目指定的时间状态为准。

## 这份数据没有说明什么

- **比较的是"模型 + 客户端"**。Astra 和 Luna 用 Codex CLI，Opus 和 Haiku 用 Claude Code，两者的工具、内置提示和上下文管理都不同。6.9 分的差距不能直接归到模型本身。
- **指标与人的判断是否一致没有验证**。分数高的模型看起来更像真值，这只在试点时肉眼核对过一道题。
- **资料是渲染出来的**。没有真实照片里的杂物、反光和镜头畸变，这里的排名在真实建筑上是否成立没有验证。
- **预算是 30 分钟墙钟**。Astra 平均用掉一半，Opus 只用七分之一；换一个预算，结果可能不同。
- **只有四个配置、一种推理强度**。
- 对象由同一个生成器的八套规则产生，题型只有三种。
